# NC-005 Execution Plan

**State:** Completed — human-reviewed and accepted on 2026-08-09

## Objective

Persist the canonical VS001 source facts and materialized `RelationshipProfile` in PostgreSQL, then provide deterministic repositories, relationship rebuild, seed load, and a one-command local demo reset without adding product APIs, recommendation logic, or graph projection.

## Files and boundaries

- `services/api/app/infrastructure/`: SQLAlchemy 2.x declarative models, session helpers, and fact/profile repositories
- `services/api/app/application/`: pure orchestration for rebuilding derived relationship profiles from persisted facts
- `services/api/app/commands/`: deterministic demo-reset command and dependency wiring
- `services/api/migrations/versions/`: one Alembic revision after the empty NC-001 baseline
- `services/api/tests/`: repository, rebuild, reset, constraint, and repeatability tests
- `services/api/Dockerfile`, `docker-compose.yml`, `Makefile`, `.github/workflows/ci.yml`: executable reset and PostgreSQL integration gate
- repository status, architecture/data, and developer-command documentation affected by NC-005

## Dependency and schema decisions

- Reuse the locked SQLAlchemy 2.x, Alembic, psycopg, PostgreSQL 17, pytest, and uv toolchain; add no dependency.
- Store all canonical fact entities required by VS001, including relational interaction participants and external identifiers.
- Store `RelationshipProfile` separately as recalculable derived data with canonical `(person_a_id, person_b_id)` primary key, model version, calculation timestamp, and the complete explainable decomposition.
- Use foreign keys, enum/check constraints, UTC-aware timestamps, source-system uniqueness, interval checks, and canonical pair-order checks at the database boundary where practical.
- Keep source-event validation in the existing pure domain model; repositories map between domain objects and persistence rows without moving formula logic into SQLAlchemy.

## Reset and rebuild strategy

1. Generate the fixed synthetic dataset in memory from the existing NC-003 generator.
2. Begin one database transaction and clear derived rows before source rows.
3. Insert the canonical source facts with stable UUIDs and source identifiers.
4. Read persisted interactions and authorized context facts through repositories.
5. Derive `relationship-v0.1.0` profiles at the dataset reference time and replace the derived materialization.
6. Commit only after the complete load and rebuild succeeds; print deterministic counts/version metadata.

The default materialized context excludes `PRIVATE` activity declarations. User-correction kinds and formula effects remain deferred; reset creates no synthetic feedback facts.

## Test strategy

- Unit/integration tests on an isolated SQLAlchemy database for fact round trips, relational participants, context visibility, profile replacement, normalized pair uniqueness, and source/derived separation.
- Reset-service tests proving repeated fixed-seed loads produce the same source/profile counts and representative relationship states.
- PostgreSQL CI steps for Alembic upgrade, two consecutive demo resets, revision reporting, and connection checks.
- Existing Relationship Engine, synthetic validation, frontend, compose, type, lint, format, and build gates remain green.

## Acceptance mapping

- Canonical source facts are persistable and reconstructable without storing synthetic relationship states.
- Interaction participants are relational and source identifiers are idempotently constrained.
- Materialized profiles retain the full decomposition, `modelVersion`, `calculatedAt`, and one canonical row per person pair.
- Rebuild uses only persisted source facts plus authorized context and produces deterministic NC-004 outputs.
- One documented command resets the demo database and can be run repeatedly without duplicates or drift.
- Facts and derived profiles remain separate; deleting/rebuilding profiles never rewrites source events.
- No NC-006+ API, projection, recommendation, graph UI, or user-feedback formula behavior is introduced.

## Assumptions

- The synthetic demo has full digital/analog collection coverage because no canonical coverage fact has been specified; the engine default is therefore used.
- Shared communities and projects are usable relationship context from persisted facts. Shared activities are included only when both declarations are non-private.
- The command targets local/demo environments; production authorization and operational seed controls are outside VS001.
